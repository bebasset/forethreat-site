FICTIONAL SAMPLE. "Harborline Analytics" does not exist. No client data, findings, or systems are depicted.

1. Executive summary

Forethreat performed a grey-box penetration test of the Harborline Analytics customer portal and its REST API between [dates], using accounts in two separate customer tenants and three roles (Viewer, Analyst, Org Admin).

Overall risk: High. Any logged-in user could promote themselves to Org Admin, and Org Admins could read and modify invoices belonging to other customers. Chained together, these two issues allow any free-trial user to access every customer's billing records. Both issues were fixed during the engagement and confirmed fixed at retest.

2. Scope & approach

  • In scope: portal.harborline.example and api.harborline.example/v2 (staging, production-equivalent data)
  • Out of scope: payment processor, corporate email, denial-of-service
  • Methodology: OWASP WSTG v4.2 and OWASP API Security Top 10 (2023); 47 API endpoints tested (coverage list in Appendix A)
  • Accounts: 2 tenants × 3 roles, provided by the client

3. Attack path

The highest-impact result came from chaining two separate issues:

  1. A Viewer in Tenant A sends "role":"org_admin" in a profile update and becomes an Org Admin (HA-02).
  2. As Org Admin, the user requests invoices by sequential ID. The API checks the role but not the tenant (HA-01).
  3. Result: any self-registered trial user can read and edit every customer's invoices, including names, addresses, and amounts.

4. Example finding detail

HA-01: Cross-tenant invoice access and modification (BOLA) HIGH 8.1

CVSS: AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:N · OWASP: API1:2023 Broken Object Level Authorization · Affected: GET|PATCH /v2/invoices/{id}

Description. The invoice endpoints confirm that the caller holds the Org Admin role, but not that the requested invoice belongs to the caller's organization. Invoice IDs are sequential integers, so every invoice can be enumerated.

Reproduction. Authenticated as Org Admin in Tenant A (org_id 1042), request an invoice owned by Tenant B:

GET /v2/invoices/88317 HTTP/2
Host: api.harborline.example
Authorization: Bearer eyJhbGciOi…[Tenant A token]

HTTP/2 200 OK
{"id":88317,"org_id":1077,"customer_name":"[Tenant B customer]","amount":"4,980.00","status":"open", …}

A PATCH with {"status":"void"} to the same ID also succeeded, so the issue affects integrity as well as confidentiality.

Business impact. Exposure and tampering of every customer's billing records. A reportable incident under most customer contracts and a likely deal-breaker in enterprise security reviews.

Remediation. Enforce object ownership on the server for every invoice operation, scoping the query by the authenticated user's org_id (e.g., WHERE id = :id AND org_id = :caller_org) rather than checking the role alone. Return 404 for objects in other tenants. Add automated authorization tests that run each endpoint with a token from a second tenant. Consider non-sequential identifiers as defense in depth (not as the fix).

Retest. Re-tested on [date]: cross-tenant GET and PATCH now return 404. The same check was confirmed on /v2/payments and /v2/exports. Status: Fixed.
